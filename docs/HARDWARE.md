# 하드웨어 사실 — 코드 수정 전 필독

모두 실기기 조사로 확인한 내용. 추측이 섞인 항목은 명시했다.
이걸 모르고 제어 코드를 고치면 모터가 폭주하거나 과열된다.

## 1. 구성

| 항목 | 내용 |
|---|---|
| 본체 | Raspberry Pi (aarch64), MK3 PTZ 카메라 / PoE 라이다 노드 |
| 모터 보드 | STM32 ("STM32-DRV"), FOC BLDC 짐벌 모터 |
| 위치 센서 | 절대 자기 엔코더 (1회전 내 절대값) |
| **전류 센싱** | **없음** ← 과열 문제의 근본 원인 |
| 시리얼 | PAN=`/dev/ttyAMA0`, TILT=`/dev/ttyAMA2`, 115200 8N1 |
| 축당 범위 | 스펙 pan ±135°, tilt 0~90° (유닛별 물리 스톱은 더 좁을 수 있음) |

## 2. 시리얼 프로토콜

| 명령 | 동작 | 주의 |
|---|---|---|
| `R\n` | 리셋 + 센서 재정렬 + **토크 해제(disarm)** | 완료까지 2~3초. 보낼 때마다 모터가 튄다 |
| `S\n` | 구동 활성화(arm) | **S도 MCU 재초기화를 유발**("MOT: Align sensor" 배너). 단순 enable이 아니다 |
| `T<rad>\n` | 목표 각도(절대값, 라디안) | 아래 3절 참고 |

**텔레메트리**: `Target angle: X, Current angle: Y, Sensor offset: Z` 형식으로
**슬루 중에만** 스트리밍된다. 정지·안착 상태에서는 거의 침묵한다.
→ **정지 상태에서는 값 없는 `T\n`(상태 조회)을 보내면 같은 형식으로 한 줄 답한다** (v2.3.0, v1.0.6 모두 — 2026-11 실측, 9절).

**펌웨어별 조회 명령 (2026-10-29 ptz018 실측)**: 펌웨어가 축마다 다를 수 있다(ptz018: PAN `v2.3.0-manual`, TILT `v1.0.6`).
v2.3.0은 아래 조회 명령을 지원한다. v1.0.6은 `?` 목록 기준 `S`, `T`, `R`, `V`, `C`(캘리브레이션 — 쓰기)만 있다 (`I`/`E`/`A` 없음).

| 명령 | 동작 |
|---|---|
| `V` | 펌웨어 버전 |
| `I` | 현재 설정(모터 타입, 한계각, 센서 오프셋, PID, voltage limit, align V, 현재 센서각) |
| `E` | 튜닝값 기본/EEPROM/라이브 비교 (`EW` 저장, `ED` 기본값 복원은 **쓰기** 명령이므로 주의) |
| `A[n]` | 센서각을 1 kHz로 n회 샘플링, 평균·p-p·std 출력 (기본 64, 최대 2000) |

`R`은 "Reset system" — **MCU 전체 재부팅**(펌웨어 배너가 다시 찍힌다). `CALIBRATE`, `M*`, `O*`, `X*`, `E*` 쓰기 명령은 운용 중 보내지 말 것.
현장 원본 바이너리(448443)는 시리얼을 읽지 않아 별도 프로세스로 출력을 엿볼 수 있었지만,
**mk3-basic 은 포트를 독점하고 직접 읽는다** — 실행 중에는 `onvif_srvd --mcu-info` 와 로그로 본다.

**arming 타이밍(벤더 실측)**: `R` → 1초 → `S` → 1초 → `T` 스트림.
`R`과 `S` 사이를 4초로 늘렸더니 arming이 실패했다(토크가 안 걸림). 이 타이밍을 지킬 것.

## 3. ★ 단발 T는 모터를 움직이지 못한다

**가장 중요한 사실.** 목표를 크게 바꾸는 `T` 한 방을 보내면 MCU는 목표를 에코하고
"슬루 중" 텔레메트리까지 내보내지만 **실제 위치는 그대로다.**

움직이는 건 **작은 스텝(≈0.02~0.2 rad)을 짧은 간격(≈10~20ms)으로 연속 전송하는 램프뿐**이다.
같은 값을 반복 전송해도 움직이지 않는다. **값이 계속 변해야 한다.**

따라서 모든 이동(부팅 위치복원, AbsoluteMove, GotoPreset, 재무장 후 복귀)은
반드시 램프 스트림으로 구현해야 한다. 이 저장소의 `tools/pantilt.py`가 검증된 참조 구현이다.

```python
# 움직인다 — 값이 연속으로 변하는 스트림
val = start
while val <= target:
    ser.write(f"T{val:.4f}\n".encode()); ser.flush()
    time.sleep(0.01)
    val += 0.05

# 안 움직인다 — 단발, 또는 같은 값 반복
ser.write(f"T{target:.4f}\n".encode())
```

## 4. ±2π 보고 프레임

절대 엔코더는 1회전 안에서만 절대값이라, 몇 바퀴 돌았는지는 모른다.
기동/정렬 시점의 자세에 따라 펌웨어가 **회전수 브랜치를 다르게 잡는다.**

- 축이 엔코더 0 경계 근처(특히 tilt 0 부근)에 있을 때 정렬되면
  이후 보고값이 **물리각 − 2π**로 나온다. (예: 물리 +160° → −200°로 보고)
- 모터 자체는 명령을 정상 추종한다. 깨지는 건 소프트웨어 쪽 각도 비교다.

**대응**: 각도 오차 계산은 전부 wrap 보정할 것.

```cpp
static inline float wrapd(float x) { return remainderf(x, TWO_PI_F); }  // [-π, π]
```

**주차 규칙**: tilt를 0 근처에 저장·주차하지 말 것. **0.1 rad(≈6°) 이상**을 유지한다.
tilt 0으로 저장했다가 부팅 복원 중 프레임이 어긋나 **2회전 폭주**가 발생한 사례가 있다
([incidents/INCIDENT-205-tilt-over90.md](incidents/INCIDENT-205-tilt-over90.md)).

## 5. 소프트웨어로 못 막는 것

- **정렬은 소프트웨어보다 먼저 일어난다.** 전원 인가/리셋 시점의 물리 자세로 각도 해석이 정해진다.
  소프트웨어 각도 제한은 **명령 공간**만 제한할 뿐, **시작 자세**에는 개입할 수 없다.
  시작 자세가 유효범위 밖이면 "정상 범위의 명령"이 물리적으로는 다회전 이동으로 번역된다.
  → **물리 스토퍼가 유일한 근본 해결.**
- **`systemctl stop onvif_srvd`로는 토크가 안 풀린다.** MCU가 마지막 `T`를 자체적으로 유지한다.
  토크를 빼려면 `R`을 시리얼로 직접 보내거나 전원을 내려야 한다.

```bash
# 모터 토크 즉시 해제 (긴급 정지)
python3 -c "import serial,time; s=serial.Serial('/dev/ttyAMA0',115200); s.write(b'R\n'); time.sleep(1)"
python3 -c "import serial,time; s=serial.Serial('/dev/ttyAMA2',115200); s.write(b'R\n'); time.sleep(1)"
```

## 6. 과열이 생기는 조건

전류 센싱이 없어서 FOC는 위치 오차를 줄이려 **계속 최대 토크를 건다.**
목표에 도달할 수 없으면(물리적 장애물, 소프트 한계가 실제 물리 스톱보다 넓은 경우)
오차가 영원히 안 닫히고 토크가 지속된다 → 발열 → 장기적으로 엔코더 열화.

특히 위험한 조합:
- 소프트 한계(±2.8 rad)가 실제 물리 스톱(예 −2.2 rad)보다 넓음 → 조이스틱을 끝까지 밀면 스톱에 눌린 채 대기
- 단발 `T`로 도달 불가 지점을 지정 → 토크는 걸리는데 텔레메트리가 안 나와 가드가 감지 못 함

## 7. 축별 특성

| 축 | 부하 | 권장 스텝 | 비고 |
|---|---|---|---|
| PAN | 낮음 | 0.05 rad / 10ms | 작은 스텝(0.02)에도 반응 |
| TILT | 중력 + 마찰 | **0.2 rad / 10ms** | 스텝이 작으면 정지마찰을 못 이겨 안 움직이거나 떨림 |

tilt에 작은 스텝을 쓰면 "안 움직인다"고 오진하기 쉽다. `pantilt.py`의 값(0.05 / 0.2)을 기준으로 삼을 것.

## 9. 기동 상태와 각도 (2026-11-02~03 실측, 비교 장비 / ptz018)

mk3-basic 의 기동 판정은 이 사실들에 기댄다 ([MK3_BASIC.md](MK3_BASIC.md)).

| 사실 | 확인 |
|---|---|
| 펌웨어는 전원 인가 후 **스스로 기동하지 않는다** — `S` 가 필요 | 비교 장비(v2.3.0 양축), ptz018 |
| 값 없는 `T` = 상태 조회. **미기동이면 `Sensor offset: 0.00`**, `Current angle` 은 원시 센서각 | v2.3.0, v1.0.6 |
| **Pi 만 재부팅하면 MCU 는 기동 상태·목표각을 유지** (MCU 전원은 그대로) | 두 장비 |
| 기동 중 `S` 를 다시 받아도 목표는 유지 (짧은 재초기화 움찔은 있음) | v2.3.0, v1.0.6 |
| `S` 후 MCU 는 저장된 목표(전원 직후·`R` 직후는 0)로 간다 → 처진 틸트를 0 까지 들어 올림 | ptz018 — 구 TILT 펌웨어에서 이때 떨림 |
| **미기동 MCU 는 `S` 전에 받은 `T` 를 무시** | ptz018 |
| **`S` 직후부터 현재 자세를 20ms 마다 `T` 로 보내면 그 자리에서 기동** (이동 없음) | ptz018 |
| v2.3.0 은 `I` 를 받으면 **미기동이어도 offset 을 채운다** → 상태 판정은 `I` 보다 먼저 | ptz018 pan |
| 콜드부팅 직후 v2.3.0 pan 이 미기동인데 offset 이 채워져 보인 경우가 있다 | ptz018 (원인 미상) |
| 각도 = wrap(원시각 − offset). `Current angle` 은 **바퀴 수가 누적**될 수 있다 (예: −4.40 = +1.88 − 2π). MCU 목표는 한 바퀴 안 값이고 MCU 도 가까운 쪽으로 제어 | ptz018 pan |
| Pi 리셋 원인 `/proc/device-tree/chosen/bootloader/rsts`: 콜드부팅 `0x1000`, `sudo reboot` `0x1020` (0x20 = 소프트 리셋) | ptz018 (CM5) |
| 틸트 방향: **0 = 렌즈가 위(돔 꼭대기)**, **π/2 = 수평 정면**. 전원이 꺼지면 틸트는 1.15~1.34 rad 근처로 처진다 | ptz018 |
| 기동 시 보드가 `MOT: No current sense.` 를 출력 (두 축, 매 기동) — 전류 센싱 없음과 일치 | ptz018 |
| 정지 상태 위치 오차: 팬 ≈0.2~0.4°, 틸트 위쪽 끝(0)은 무게·마찰로 마지막 2~3° 가 늦게 붙음 | ptz018 |
| 전원 인가 후 9~14초쯤 "딱딱" 소리는 onvif 가 아무것도 보내지 않아도 난다 — 하드웨어 자체 | ptz018 |
