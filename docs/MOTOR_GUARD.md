# 모터 과열 보호 (Kestrel 모터 펌웨어 v2.4.0+)

라이다 모델(Kestrel) 팬/틸트 모터 보드의 온도 추정·과열 보호 정리.
출처: 제작사 안내 메일 (2026-11-10). 원문은 `_workspace/reference/제작사_모터과열보호_안내_2026-11-10.md`.
"우리 확인"이라고 적은 것은 우리가 장비에서 직접 본 것이다.

## 2. 동작

- **온도는 추정값이다.** 보드에 전류 센서도 온도 센서도 없다([HARDWARE.md](HARDWARE.md) 1절).
  - 모터에 거는 전압 Vq로 발열을 계산한다: P ≈ 1.5 × Vq² / R.
  - 이 발열로 열 모델을 돌려 10 ms마다 모터 온도를 추정한다.
- **70 °C에서 트립한다.** 모터를 끄고 두 시리얼 포트에 아래 줄을 보낸다.
  `Guard: motor temperature estimate 70 C. Motor disabled. Send S to restart after it cools.`
- **자동으로 다시 켜지지 않는다.**
  - 55 °C 아래로 식기 전에는 `S`를 거부한다(냉각 중). 트립 뒤 약 8분 걸린다.
  - 식은 뒤 호스트가 `S`를 보내야 다시 돈다.
- **추정 온도가 유지되는 범위:** `R`을 보내거나 펌웨어를 다시 올려도 추정 온도는 그대로다. 전원을 완전히 껐다 켜야 실내 온도 설정값에서 다시 시작한다.
- **발열 기준:**
  - 실내 온도 설정은 유닛마다 27 °C로 저장돼 있다.
  - 27 °C 기준으로 계속 견딜 수 있는 발열은 약 **6.9 W**다.
  - 제작사는 셋업 때 모든 각도에서 유지 발열이 **5.5 W 이하**가 되도록 맞췄다.
- **제작사 요청:**
  - 설치 뒤에는 케이블 장력, 기구 간섭, 바람 때문에 이동 범위 중간에서도 저항이 생길 수 있다.
  - 운영 중에 추정 온도와 발열을 주기적으로 봐 달라고 했다.
  - 특정 각도에서 발열이 계속 높거나 온도가 꾸준히 오르면 제작사에 알린다.

> 우리 확인 (2026-11-09, poe002): 박스 안에서 옛 ONVIF가 팬을 박스 벽에 대고 밀자 과열 보호가 동작했다.
> 같은 장비에서 케이블이 바스켓에 걸렸을 때는 Vq가 전압 한계(10 V)까지 올라가는 것을 Q로 확인했다. 제작사가 말한 "이동 중간의 저항"이 바로 이런 경우다.

## 3. 터미널로 보기 (CM5에서)

```bash
sudo systemctl stop onvif_srvd                                    # onvif_srvd 가 UART 를 잡고 있으면 안 됨
python3 -m serial.tools.miniterm /dev/ttyAMA0 115200 --eol LF -e  # 팬 (틸트 = /dev/ttyAMA2), 종료 Ctrl+]
sudo systemctl start onvif_srvd                                   # 끝나면 반드시 다시 켬
```

- 명령 끝에는 LF가 필요하다. 그래서 `--eol LF`를 꼭 붙인다. `screen`은 CR을 보내서 동작하지 않는다.
- 우리 규칙([HARDWARE.md](HARDWARE.md)):
  - `systemctl stop`만으로는 토크가 풀리지 않는다.
  - 틸트를 0° 아래로 보내지 않는다.
  - 승인 없이 쓰는 명령은 V/T/I/Q/E 조회만이다.

| 명령 | 동작 |
|---|---|
| `S` | 모터 시작 (저장된 캘리브레이션·튜닝 적용). 냉각 중이면 거부 |
| `R` | 컨트롤러 리셋. 다시 돌리려면 `S` |
| `T<rad>` | 목표 각도. 범위를 넘으면 끝 값으로 자른다. 기본 범위: 팬 ±2.238, 틸트 0 ~ 1.492 (유닛마다 더 좁을 수 있음, 예: 005 틸트 0.06 ~ 1.48) |
| `I` | 설정·상태. 온도는 `Guard:` 줄에 나온다 (아래) |

```
Guard: GL35 (by axis) estimate 41.6 C (room 27.0 C, trip 70 C), heat 0.01 W, trips since boot 0
       모터 모델          추정 온도     실내 설정     트립 온도      지금 발열    부팅 후 트립 횟수
```

## 4. Q 상태 (프로그램용)

- **요청과 응답:** `Q\n`을 보내면 `Q` + 16진 64자 + CR LF로 답한다.
  - 내용은 32바이트 little-endian 레코드다.
  - 끝 2바이트는 앞 30바이트의 CRC-16/CCITT다(다항식 0x1021, 초기값 0xFFFF).
- **응답 포트:** 답은 요청한 포트로만 온다.
- **섞여 오는 텍스트:** 같은 포트에 과열이나 드라이버 오류 알림 텍스트가 섞여 올 수 있다. 그래서 **`Q`로 시작하고 길이가 65자인 줄만** 해석한다.
- **폴링 간격:** 답 하나에 약 6 ms가 걸리고 그동안 제어 루프가 멈춘다. **20 Hz 이하**로 묻는다.
- **해석 도구:**
  - Python struct 형식: `"<BBHhhhhHhHhhHHIH"`.
  - 디코더 `kestrel_status.py`는 유닛의 `~/cm5-setup/`에 있다. `query(port)`는 dict를 돌려주고, 응답이 없거나 CRC가 틀리면 None이다.
  - 명령줄에서 `./kestrel_status.py`를 실행하면 두 축 상태를 계속 보여 준다.

| 오프셋 | 필드 | 형 | 단위 |
|---|---|---|---|
| 0 | 레이아웃 번호 | u8 | 1 |
| 1 | 시퀀스 | u8 | Q마다 +1 |
| 2 | 플래그 | u16 | 아래 표 |
| 4 | 목표 각도 | i16 | mrad |
| 6 | 현재 각도 | i16 | mrad |
| 8 | 속도 | i16 | mrad/s |
| 10 | 인가 전압 Vq | i16 | mV |
| 12 | 전압 한계 | u16 | mV |
| **14** | **모터 추정 온도** | i16 | 0.01 °C |
| **16** | **발열 추정** | u16 | 0.01 W |
| 18 | 실내 온도 설정 | i16 | 0.01 °C |
| 20 | 트립 온도 | i16 | 0.01 °C |
| 22 | 부팅 후 트립 횟수 | u16 | |
| 24 | FOC 루프 속도 | u16 | Hz |
| 26 | 가동 시간 | u32 | ms |
| 30 | CRC-16/CCITT | u16 | |

| 플래그 bit | 뜻 |
|---|---|
| 0 | 동작 중 (모터 켜짐) |
| 1 | 캘리브레이션됨 |
| 2 / 3 | 팬 / 틸트 보드 |
| 4 | 드라이버 오류 (`F`로 해제) |
| **5** | **과열 트립** (다음 `S`까지) |
| **6** | **냉각 중** (`S` 거부) |
| 7 | 튜닝 저장됨 |
| 8 | v2.x 보드 |
| 9 | GB2208 모델 (v2.5.3에서 생김) |
| 10 | 각도 방향 반전 (v2.5.3 `CF1`) |

우리 확인 (실측 플래그가 위 표와 맞다):

| 장비 | 축 | 펌웨어 | 상태 | 플래그 | 켜진 비트 |
|---|---|---|---|---|---|
| poeio-2610-005 | 팬 | v2.5.3 | 꺼짐 | 0x0386 | 1, 2, 7, 8, 9 |
| poeio-2610-005 | 틸트 | v2.5.3 | 꺼짐 | 0x018A | 1, 3, 7, 8 (GL35) |
| poe002 | 팬 | v2.5.1 | 꺼짐 | 0x0186 | bit 9 없음 |

- 켜지면 bit 0이 선다. `pt_full_measure.py`는 이 bit로 켜짐을 판정하는데, 매번 S 뒤 약 2.1초에 확인됐다.

## 5. onvif_srvd v1.0.0 (지금 배포판)과의 관계

| 항목 | 지금 동작 |
|---|---|
| 켜짐 판정 | Q bit 0 (`q_run_bit = 0x0001`). 제작사 안내로 맞는 비트임을 확인 ([PTZ_STREAMING.md](PTZ_STREAMING.md)) |
| 운영 중 트립 | bit 0이 꺼짐 → GetStatus `Error = MOTOR_OFF` + `PTZ-ALERT`. **자동 재시작(S) 안 함**. 사람이 확인한 뒤 ONVIF를 재시작하거나 `S` |
| 온도·발열 기록 | **안 함.** Q의 오프셋 14/16을 읽지 않는다 |
| `Guard:` 텍스트 | 해석하지 않는다. Q가 65자 줄만 해석하므로 섞여 와도 문제없다 |
| 폴링 간격 | 0.5초 (2 Hz) → 20 Hz 제한 안 |
| S 뒤 대기 | v2.5.x는 S 뒤 약 2.1초 동안 T를 무시한다 ("Motor ready" 문구 뒤에도). mk3-basic은 3초 동안 지금 자세를 계속 보내서 문제없다 (우리 확인 11-09) |

## 6. 모터 헬스 기능 — v1.1.0 (빌드 `a8e37f1f`, 브랜치 `feat/motor-health`)

onvif_srvd가 이미 쥐고 있는 UART로 Q를 묻는 방식이다. 그래서 터미널처럼 onvif_srvd를 멈출 필요가 없다.
Q 펌웨어(v2.4+) 축에만 동작한다. 구형 펌웨어(Pro v2.3.0 / v1.0.6)는 지금과 똑같이 동작한다. **모터 명령은 하나도 추가하지 않았다.**

| 항목 | 동작 |
|---|---|
| 조회 | 기존 0.5초 감시 스레드가 축마다 `Q`를 보낸다 (2 Hz, 제작사 한도 20 Hz 안). 전에는 켜짐 비트가 확인된 축만 물었다 |
| 실시간 | `/run/onvif_srvd/live` (`--mcu-watch`)에 축별 한 줄: `motor 31.2 C (trip 70) heat 0.42 W Vq 1.20/10.0 V trips 0 [OVERHEAT-TRIP COOLING DRIVER-FAULT HEAT-WARN TEMP-WARN]` |
| 파일 | `/run/onvif_srvd/motor_health.json` (1초): 축별 `temp_c heat_w vq_v vlim_v room_c trip_c trips running overheat_trip cooling driver_fault flags heat_warn temp_warn foc_hz board_uptime_s` |
| MQTT | `telemetry/<id>/ptz_health` (10초), 위 JSON과 같다. 단 edge `onvif_start.sh`가 브로커를 127.0.0.1로 두므로, 현장에서는 edge가 JSON 파일을 읽어 올리는 쪽이 현실적이다 |
| 주기 로그 | `PTZ-HEALTH:` 5분마다. 축별 현재값과, 그 사이 **최고 온도·발열 및 그때 자세** (어느 각도에서 힘든지 보인다) |
| 경보 (바뀔 때 한 번) | 과열 트립(bit 5), 냉각 끝(bit 6 해제), 드라이버 오류(bit 4), 트립 횟수 증가, 발열 ≥ 5.5 W가 30초 이상, 추정 온도 ≥ 60 °C. 보드가 보내는 `Guard: ...` 줄도 그대로 `PTZ-ALERT` |
| GetStatus | 트립이나 냉각으로 꺼지면 Error = `MOTOR_OVERHEAT` (전에는 `MOTOR_OFF`) |
| 자동 재시작 | **없음.** 식은 뒤 `PTZ: ... cooled down`이 찍히면 원인을 확인하고 onvif_srvd를 재시작한다 |

`ptz_watch.conf`로 바꿀 수 있다 (없으면 기본값):

```
heat_warn_w  = 5.5    # 발열 경고 기준 W (0.5 ~ 20)
heat_warn_s  = 30     # 그 이상이 이만큼 이어지면 경고 (초)
temp_warn_c  = 60     # 추정 온도 경고 (30 ~ 69)
health_log_s = 300    # PTZ-HEALTH 주기 (초), 0 = 끔
```

**확인한 것 (11-10):**
- Debian 12 컨테이너 빌드에서 경고 0.
- Q 해석: 005 실측 2줄이 제작사 struct `"<BBHhhhhHhHhhHHIH"` 해석과 모든 필드가 같았다. 추정 온도 27.74 °C는 `I`의 27.7 °C와 맞다. CRC가 틀린 줄은 버린다.

**poe002 실장비 시험 (11-10, 모터 v2.5.1, 빌드 `3d4d8118`, 원래 바이너리 백업 `~/onvif_backup_20261110/onvif_srvd_110df0c5`):**
- **설치와 시작:** Q로 켜짐을 판정했다. 처음 시작에서는 S를 보내고 자세를 유지했다. 이후 재시작에서는 모터 명령 없음.
- **출력:** 첫 `PTZ-HEALTH` 줄, live 파일 축별 줄, JSON 1초 갱신을 모두 확인했다.
- **경보 경로:** 기준을 낮춰(0.5 W/3초, 30 °C, 기록 20초) 전 범위로 움직였다.
  - 발열 경보와 온도 경보가 축별로 한 번씩 났다.
  - 가운데로 돌아오면 `heat back to normal`이 찍혔다.
  - 시험 중에 해제 기준 버그를 찾아 고쳤다. 해제 기준이 '경고값 − 0.5 W'라 경고값이 낮으면 0이 됐다. 지금은 '경고값 × 0.8'이다.
- 시험이 끝난 뒤 설정 파일을 지우고 기본값으로 재시작했다.
- **실측: 멈춰 있을 때 발열** (틸트 45°, 20초씩)

| 자세 | 팬 | 틸트 |
|---|---|---|
| 팬 가운데 | 0.02 W | 1.9 ~ 2.0 W |
| 팬 왼쪽 끝 −126° | **2.8 ~ 4.3 W** (Vq −3.5 ~ −4.5 V) | 1.9 W |
| 팬 오른쪽 끝 +126° | **2.3 ~ 3.4 W** (Vq +3.3 ~ +4.0 V) | 1.8 W |
| 틸트 85° (정면 수평) | 0 W | **3.9 ~ 4.7 W** (자중) |

  → 팬은 가운데에서 거의 0 W인데 양 끝에서 2~4 W를 계속 쓴다. 끝에서 케이블 장력을 받는 것으로 보인다. 제작사 기준 5.5 W 아래지만 여유가 작다. 케이블 수리 뒤 상태이므로 기준값으로 기록해 둔다.
  - 추정 온도는 시험 내내 최고 36 °C였다 (트립 70 °C).
  - 끝에 오래 머무는 운용(프리셋)이라면 이 발열이 계속 이어진다.
